# Architecture

Single executable target `Pulse` at `Sources/Pulse`. No internal modules. The floating monitor is **not** a SwiftUI `WindowGroup` scene.

Provider routes, credentials, cookies, and extra-account OAuth belong in [providers/README.md](providers/README.md). This file is the AppKit shell and the settings/state that every provider shares.

## App shell

- `PulseApp.swift` — `@main`. Supplies the required empty SwiftUI Settings scene, but replaces its standard command so Command-, opens the AppKit-owned settings window rather than the empty scene. **Check for Updates…** is the next item after About and calls `AppUpdate.check`, the same path as Settings → About. The AppKit delegate owns the `NSStatusItem` (Settings, Quit) so `AppSettings.hidesMenuBarIcon` can remove it at runtime. Usage is shown solely in the floating panel; when the icon is hidden, the panel menu or a registered global shortcut remains an entry point.
- `AppDelegate.swift` — activation policy `.accessory` unless **Always show Dock icon** is on, in which case `.regular` is set in `applicationWillFinishLaunching` (no Dock icon otherwise, except while the main window, a recap, the service chooser, or Sparkle's update window is open — see Settings window and `App/DockPresence.swift`). A manual launch, a Dock click, and a reopen open the main window; a login launch does not, unless **Show main window when opened at login** is on (`LaunchPlanner`). Owns `AppSettings`, `PanelPlacement`, `FloatingPanelController`, the main window and the recap window (`RecapWindowController`, opened from the Token spend pane's recap button or a clicked recap notification; neither menu carries an entry for it). Closing the last window does not quit (`applicationShouldTerminateAfterLastWindowClosed`). Ignores `SIGPIPE` process-wide so a helper (for example Codex app-server) exiting cannot take Pulse down with it (`Terminated due to signal 13`).
- `FloatingPanelController.swift` — owns a custom `NSPanel` (`FloatingPanel`: borderless, non-activating, `canBecomeKey` / `canBecomeMain` both false) hosting SwiftUI through `NSHostingView`. **The AppKit controller computes and animates the panel frame.** SwiftUI has no say over outer size; expand/collapse is `NSAnimationContext` / `panel.animator()`, not a SwiftUI transition.
- Full-screen Spaces: `AppSettings.hidesInFullScreen` selects `.fullScreenNone` (default) or `.fullScreenAuxiliary`. Both keep `.canJoinAllSpaces` for ordinary desktops. This is public window collection behaviour, not a guessed full-screen detector.
- Screen capture: `AppSettings.hidesFromScreenCapture` (Settings → Position and behavior, **Hide from screenshots**, off by default) sets the panel's `sharingType` to `.none`, else AppKit's default `.readOnly`; the window list then reports `kCGWindowSharingState` 0 and capture skips it. The reason is the frame: sized for the tallest card ([ui/panel-geometry.md](ui/panel-geometry.md)) and mostly transparent, it is what a screenshot tool's automatic window selection picks. Off by default because it also keeps Pulse out of its own README images and bug reports. **A request, not a guarantee:** Apple says not to rely on `.none` to exclude a window from capture, and since macOS 15.4 ScreenCaptureKit can still include it ([`sharingType`](https://developer.apple.com/documentation/appkit/nswindow/sharingtype-swift.enum/none), [DTS](https://developer.apple.com/forums/thread/792152)). Tools that read the sharing state skip the panel, which is the point; the subtitle promises that and no more, and says recordings and screen sharing may still show it.

`LSUIElement` must be **true** in the bundled `Info.plist`. Setting `.accessory` in code runs after the Dock has already been told what to show, so without the key a Dock icon flashes at every launch. The key stays true when **Always show Dock icon** is on: `applicationWillFinishLaunching` calls `DockPresence.launchPolicy`, which is `.regular` only for that switch, early enough that the icon appears with the launch instead of after the first window. Shipping detail: [releasing.md](releasing.md).

## Settings window

Hand-rolled `SettingsWindowController`, not SwiftUI’s required empty `Settings` scene: an `.accessory` app must `NSApp.activate` or the window opens behind everything. The `.appSettings` command is replaced in `PulseApp`, so the standard keyboard command reaches this controller too.

**The menu bar names Blinky once a tracked window is shown, and the window is in front of other apps.** The usage panel is non-activating, so a click on its icon does not make Blinky frontmost. `setActivationPolicy(.regular)` is not visible to the menu bar until the next turn; activating in the same turn leaves the previous app's name up while the window title already says Blinky. `MainWindowActivation` waits that turn when the policy has just become `.regular`, and activates immediately when Blinky is already regular. Staying `.accessory` — Show Dock icon while a window is open is off, and Always show Dock icon is off — has no application menu to claim; the window is still ordered in front (`orderFrontRegardless`). `makeKeyAndOrderFront` only orders among Blinky's own windows, which left the main window behind the app that was key. The window being shown counts as open before it is visible, so this same call becomes `.regular` when the while-open Dock switch allows it. Every show of the main window goes through `SettingsWindowController.show` → `DockPresence.apply(showingWindow:)`: the usage card's grid icon, the panel menu's Settings…, the menu bar item, ⌘,, a cold launch, a Dock click, a reopen, `pulse://settings`, and a clicked notification. The recap, the service chooser, and the Token spend window use the same call. An update offer calls `apply()` with no window and then `orderFrontRegardless` on Sparkle's window; a policy change still waits a turn.

**Dock icon while open.** An `.accessory` app has no Dock icon and no ⌘-Tab entry, so a window another app covered could not be found again. With `AppSettings.showsDockIconInSettings` (**on by default**, key `settings.showsDockIconInSettings`, callback `onDockIconChange`, never `onChange`) `DockPresence` (`App/DockPresence.swift`, one owner for every window Pulse opens — the main window, the service chooser, and the [recap window](recap.md#the-window)) switches to `.regular` when a tracked window shows and back to `.accessory` when the last closes (`SettingsWindow.close()` / `RecapWindow.close()` / the chooser's `windowWillClose` name the closing window, which still reports visible). `AppSettings.alwaysShowsDockIcon` (**off by default**, key `settings.alwaysShowsDockIcon`, the same callback) keeps `.regular` the whole time, including at launch (`DockPresence.launchPolicy`) and with every window closed; while it is on, the while-open switch is hidden and its stored value is left alone. Sparkle's update window is not tracked; while that session is showing, `setUpdateOfferVisible(true)` keeps `.regular` even if both Dock switches would otherwise say accessory, and the session's end clears it ([releasing.md](releasing.md#sparkle)). A minimised window counts as open, and flipping either switch applies at once. `LSUIElement` stays true, so a launch with Always show off puts nothing in the Dock until a window asks. **The Dock's Quit closes the windows, not Pulse** (`DockQuit`, `applicationShouldTerminate`, 2026-10-15): the icon stands for the windows, and quitting the app from it took the panel away from someone who meant to close the main window. Told apart by the quit Apple event's sender being the Dock with no quit reason; ⌘Q, the app menu and the menu bar icon's Quit still quit, and so do logout, restart and shutdown (loginwindow, with a reason). Always show Dock icon does not change that.

- **The title bar and toolbar are SwiftUI's**: the window's content is an `NSHostingView` with `sceneBridgingOptions = [.toolbars, .title]`, `.fullSizeContentView`, `toolbarStyle = .unified`. The title is **Blinky** (`navigationTitle`, the same in every language), and the toolbar's items are **back and forward** (`SettingsNavigation.back` / `forward`, ⌘[ and ⌘], skipping an account removed since it was visited). The open pane's name stays in the sidebar. A built-in account draws its title and Back in the pane; the sidebar keeps Providers selected. The window opens on the pane last shown, and on **Appearance** when nothing has been stored. A hosting *view*, not a controller: with a controller the window binds its title to the controller's, which is nil.
- That is what gives System Settings' look on macOS 26: **the sidebar runs up behind the traffic lights, and scrolled content fades softly out under the title.** Measured in a harness (2026-10-15), each alternative missed one half. An `NSToolbar` made in AppKit put the sidebar up top but drew a hard band and line under the title — the soft fade is SwiftUI's, and SwiftUI cannot see a toolbar it did not make. **A toolbar with no items is not drawn**, and without one the sidebar stops under the title bar, so the toolbar must carry at least one item. A transparent title bar turns the fade off and prints scrolled content over the title. `.toolbar(removing: .sidebarToggle)`: the sidebar cannot be hidden. Every variant measured, and how the answer was found: [decisions/settings-window-title-bar.md](decisions/settings-window-title-bar.md).
- No extra top padding: the toolbar is a safe area and the scroll view insets by it.
- Ending text-field editing on click-away is the **window’s** job (`SettingsWindow.sendEvent`). Geometry against the field being edited, never `hitTest` — a hosted SwiftUI tree answers that unreliably. See [ui/settings.md](ui/settings.md).

## Ways into settings

Four, and the menu bar is only one of them — an icon in a full menu bar is not reachable at all ([issue #24](https://github.com/qunqin24/Pulse/issues/24)):

- The AppKit status-item menu (`AppDelegate`), unless the user has hidden its icon.
- A **secondary click on the rail**, which puts up `AppDelegate.panelMenu()`. [ui/input.md](ui/input.md)
- A **global shortcut**, unset until somebody sets one. `GlobalShortcutMonitor`, held by the app delegate for the life of the process and re-applied by the settings pane whenever a combination changes. The panel's own shortcut goes through `settings.isPanelVisible` rather than `FloatingPanelController.toggle()`, so the panel is in the state the switch in settings claims and stays that way across a launch.
- A `pulse://` link, below.

The first three are kept as an invariant: if no selected provider can supply a visible panel and neither shortcut was actually accepted by the window server, Pulse restores the menu bar item. A stored combination that conflicts with another app does not count. Hiding the icon from Settings first shows the panel when it would otherwise remove the last visible entry point; before the initial provider choice, where no panel exists, the request is refused. Later hiding that panel, clearing the last shortcut, a registration failure, or restoring an unsafe saved combination brings the icon back.

## Settings navigation from other apps

`PulseLink` parses `pulse://settings`, `pulse://integrations`, and `pulse://account/<encoded-id>`. `AppDelegate.application(_:open:)` passes accepted links to `SettingsWindowController`, whose `SettingsNavigation` owns the selected pane shared with SwiftUI. A request id lets a repeated link clear sidebar search and return to the heading, even when the pane is already selected. Account targets must exist in `settings.allAccounts`; links never create a slot or run a repair. `Scripts/bundle.sh` registers the `pulse` URL scheme in `CFBundleURLTypes`. Setup and examples: [integrations.md](integrations.md).

## Settings and persistence

`AppSettings` is `@Observable`, stored in `UserDefaults` (`AppSettings.defaults`, `.standard` for the app and a throwaway suite in tests, so a test never writes the real preferences).

**One class, nine files.** Swift keeps stored properties in the class body and `@Observable` tracks only those, so `App/AppSettings.swift` is the single list of everything stored — each setting's declaration and doc comment, grouped by topic — plus the init and `restored()`. Each setting's `didSet` is one line calling `<name>Changed(from:)`, and that handler lives in its topic's file together with the topic's keys (`AppSettings.Key`), shipped defaults (`AppSettings.Default`), per-account accessors and restore code: `+Application` (menu bar item, Dock icon, shortcuts, language), `+Panel` (visibility, size, rail metrics, glass, `PanelMetrics` upkeep), `+Rings` (tints, marks, clock, warning colour, pinned window), `+Accounts` (which accounts exist, which are shown, order, `StoredRail`, `removeAccount`), `+Providers` (routes, sites, balance basis, proxy, cadence), `+TokenSpend`, `+Notifications`, `+Recap`, `+WindowStarter`. Three observers (`glassTransparency`, `recapMonthlyPrice`, `enabledAccounts`) stay inline in the main file: they assign to themselves inside `didSet`, which does not re-run the observer, and from a method it would. The memberwise `init` keeps its flat labelled list — callers (`AppSettings(readsTokenSpend: true)`) rely on it, and stored properties must be assigned in the initializer's own body — but its literal defaults are the same `Default` constants `restored()` falls back to. Keys are the stored format; `AppSettingsPersistenceTests` spells them out and round-trips every setting through `restoredSettings(from:)`. A new setting is: a stored property in the main file, a `Key` and (if literal) a `Default` in its topic file, its `…Changed(from:)` there, and its read in `restoredSettings`.

**Two callbacks.** `onChange` is how AppKit hears about settings that change what is fetched or which accounts are shown: `AppDelegate.settingsChanged` re-places the panel **and** `UsageStore.settingsChanged` refreshes every provider. `onLayoutChange` is for settings that change only how the panel is drawn or placed — `panelSize`, `railSpacing`, the rail's figure and end-style switches, `showsWindowClock`, `showsForecast`, `usageBarStyle`, `detailedCards`, `usesGlass`, `autoCollapse`, `hidesInFullScreen`, `followsActiveDisplay`, `snapsToEdges`, `showsSecondRing`: `AppDelegate.layoutChanged` only re-places the panel (`FloatingPanelController.settingsChanged`) and fetches nothing. They all used to share `onChange`, so choosing a panel size cost every provider a request for figures that had not moved. `AppSettingsLayoutTests` pins which callback each setting fires. The `PanelMetrics` writes in those handlers happen only on the instance the app is drawn from (`drivesPanelMetrics`, set by `restored()`), so a preview's or a test's `AppSettings` cannot resize the panel; the currency's `Money` writes follow the same rule, and the currency uses neither callback — the panel rebuilds through `moneyIdentity` in its `.id` ([refresh-and-data.md](refresh-and-data.md#currency)). `hidesMenuBarIcon` and `showsUsageInMenuBar` are the exceptions: their dedicated callback (`onMenuBarIconChange`) removes, restores or redraws the AppKit status item without refetching providers. With `showsUsageInMenuBar` on, `AppDelegate.showMenuBarReading` draws `MenuBarReading.choose` — `menuBarAccount` while it is on the rail, else the fullest headline window among the shown accounts, skipping unavailable readings and inferred (`estimate`) rings — as that provider's template mark and its percentage, a small ring or its split timed limits (`menuBarStyle`), `systemRed` at the warning threshold or when spent, and re-arms `withObservationTracking` on every change. `menuNeedsUpdate` puts `MenuDashboard` (an `NSHostingView` that resizes the item as its tab changes), the usage-page item and **Refresh** at the top of the status item's menu only; see [ui/settings.md](ui/settings.md). It defaults to `false` to preserve the existing menu bar entry point. With no reading to show, the status item is **Blinky's own mark** — the mascot, drawn in colour from `blinky-mascot.png` at 18 pt (`MenuBarReading.mascotMark`) — which replaced the SF Symbol `chart.pie.fill`, a stand-in that looked like nothing the app is.

- Once monitoring starts the **rail** must not be empty (nothing to hover, nothing to grab). Before the initial choice, an empty account set is valid and the panel is not created. An added account alone is a valid rail; rebuilding from `Provider.allCases` must never overwrite that choice.
- `providerOrder` / `orderedAccounts`: never trust the stored list as written. Drop unknown names; append accounts the list does not mention **in name order** after whatever arrangement is stored. The settings sidebar follows the same order. Reorder does **not** call `onChange` — that path refetches everything.
- **First run and upgrade offers** are resolved by `ProviderSelection.restore`, called from `AppSettings.restored`. First launch enables nothing. An empty or invalid saved set returns to the chooser, never to an everything-on fallback. Discovery suggests providers but enables none; see the startup contract below.
- A provider with nothing fetched yet is **not** seeded `.loading` (`UsageStore.initialState`). Loading that never resolves is a lie on its settings pane.
- Each enabled provider pane has its own refresh control. A switched-off provider is not fetched by the timer, the settings pane, or `UsageStore.refresh(_:)`; its Current usage group says **Not shown** instead of leaving a permanent loading placeholder.
- Where a provider has more than one route, which one is used is `AppSettings.source(for:)` (`UsageSource`). `.automatic` is the default: take the primary route when it can, fall back when it cannot. Pinning reports failure instead of quietly answering from elsewhere. Which routes exist: [providers/README.md](providers/README.md).
- `networkProxy` is one persisted value rather than four independently firing fields. It configures Pulse's external sessions and supported helper processes, then `onChange` queues a full refresh. Scope and the Sparkle exception: [networking.md](networking.md).
- Colour means usage, not brand (`UsageTint`, optional per-account `RingTint`). Spent colour still wins. Spent comes from the **provider’s flags**, not from crossing 100%. See [ui/rings-and-surface.md](ui/rings-and-surface.md).
- The rail ring shows one window: closest to limit, or a pin (`AppSettings.pinnedWindows`). Resolved at display time.

`AccountKey` is provider plus which account. The primary account’s id is the provider’s `rawValue` so stored prefs and cache files need no migration. Extra accounts: Claude Code, Codex, Grok, Grok Bot only (`supportsMultipleAccounts`). How those logins work: [providers/README.md](providers/README.md).

Keys pasted in Settings live in `keys.dat` (`APIKeyStore`), not `UserDefaults`. Extra-account tokens live in `accounts.dat`. Both are AES-GCM, owner-only, key derived from the Mac. **Each store changes its file under one lock** (read, change one entry, write back): Settings saving a key and a console session renewed in the background used to race, and the later write dropped the other's key. A background renewal replaces a credential only while it still holds the one it renewed (`APIKeyStore.replaceKey`, `AccountCredentials.renewed`), so one removed or retyped meanwhile is not written back. Pinned by `APIKeyStoreTests`, in a temporary folder.

## Provider choice before monitoring

`ProviderSetupWindowController` hosts the chooser in a regular AppKit window and registers it with `DockPresence`, so it has a Dock icon and a ⌘-Tab entry on the same rule as the main window. On first launch it lists all providers, unchecked, with detected installations first. **Done** needs at least one selection. Closing it or choosing **Not now** leaves the rail absent and the menu bar usable; until a service is chosen, the menu bar menu leads with an item that reopens the chooser, since nothing else on screen says why there is no rail; enabling a service in its Settings pane also completes the initial choice. Dismissing an initial chooser is not saved as completion: the next launch asks again.

A **login launch** does not show the chooser, the status-line offer, or the Claude desktop keychain prompt. Those wait for the next manual open or a reopen (`LaunchPlanner`, `holdFirstRunPrompts`). A fresh install still gets the chooser then, because no service has been chosen. An upgrade suggestion is stamped offered at restore; when the login launch defers the chooser, that stamp is put back (`offeredProvidersBeforeStamp`) so quitting without a manual open does not spend the offer unseen. A manual launch, and a launch whose kind could not be told, show the main window and any chooser that is due.

The startup gate is the resolved account set, `AppSettings.needsProviderSelection`, not whether any window was dismissed. `AppDelegate` creates the panel and starts `UsageStore` only after that set is non-empty. Store construction seeds placeholders without looking for credentials; `start`, both refresh entry points, and settings-driven refresh also refuse an empty selection. Provider panes load credentials and history automatically only for enabled primary accounts; opening Codex's pane while disabled cannot start its helper. Connection, sign-in, diagnostics and usage controls are built only after the initial choice, so even evaluating their contents cannot read a tool's configuration beforehand. The separate Token spend pane keeps its own workflow.

Claude's desktop Keychain request and status-line offer run only after the primary Claude Code account is enabled, including when enabled later through Settings. A login launch holds both until a manual open or a reopen. A new grant's callback checks it is still enabled before refreshing. Per-provider access descriptions and exact discovery paths belong in [providers/README.md](providers/README.md).

Upgrades preserve the saved enabled account ids, including extra-account-only rails. A provider new to `settings.offeredProviders` is **suggested once**, and only if presence-only discovery found it; existing providers continue monitoring while that chooser is open. Dismissal keeps the existing set. Undetected new providers remain available in Settings. All current providers are stamped as offered during restoration, so a declined upgrade offer does not recur. A login launch that deferred the chooser puts the previous offered list back first, and stamps again when the chooser is actually shown.

**Extensions** are found by `ExtensionCatalog.scan` at launch, before the saved choice is restored, so an extension's account id counts as known and its switch survives; a folder that is gone takes the switch with it on the next launch. They are never in the chooser or in an upgrade offer — `Provider.builtIn` leaves the type out — and a new one starts off. [extensions.md](extensions.md)

**Legacy 1.0.0:** it wrote an offered list but no enabled list until the user edited one. Only an **absent** enabled key is restored from that historical offered list. An explicit empty array, malformed value or unknown-only list goes to the chooser. There is no path that enables all current providers as a recovery strategy.

## Login item

`LoginItem.swift` — on by default, decided **once** (own flag; never re-enable on a later launch). Reads the *system* state, not a stored preference.

- Bundled app: `SMAppService.mainApp` (what System Settings lists).
- `swift run`: that API reports `notFound`. A launch agent is written to `~/Library/LaunchAgents` instead. No `KeepAlive`.
- Rebuilding moves the executable; `repairPathIfNeeded` rewrites a stale agent. `LoginItem.adoptBundleIfNeeded` stops a leftover agent and `SMAppService` both launching after an upgrade.
- `InstalledAppName` moves an installed `Pulse.app` to `Blinky.app` on launch when that name is free in the same folder, then relaunches from the new path. Open at login was path-based, so the relaunched copy registers the bundle that is running (`LoginItem.refreshAfterBundleMoved`, `SMAppService.mainApp`). The switch, if that register does not stick, is Settings → General → Startup and windows → Open at login (zh-Hans 开机启动). [releasing.md](releasing.md)

**Telling a login launch from a manual one.** `SMAppService` does not say why the process started. `LaunchClassification` reports `.login` only on a positive signal, and `.uncertain` is treated as a manual launch so the main window still opens (`LaunchPlanner.onLaunch`):

1. `keyAELaunchedAsLogInItem` (`'lgit'`) on the `kAEOpenApplication` event, read by a handler installed in `applicationWillFinishLaunching` and from `currentAppleEvent` if the event is already current. Present and true is a login launch. Present and false is a manual launch. The open event with the flag absent is also a manual launch — that is how Finder, Spotlight, Launchpad and `open -a` start the app — unless the parent process is a known login launcher, because `SMAppService` has been seen to omit the flag.
2. The parent process, when the event could not be read. `loginwindow` and BackgroundTaskManagement (`backgroundtaskmanagementagent`, `backgroundtaskmanagementd`) count as a login launch. Finder, Dock, Spotlight, Terminal and `open` count as a manual launch. **`launchd` does not count**: on current macOS it is the parent of an ordinary GUI launch as well.

Anything left is `.uncertain`, and the window opens. The panel and the menu bar item are unaffected either way. **Show main window when opened at login** (off by default) is the only case in which a confirmed login launch opens the main window; the first-run prompts stay deferred on every login launch.

## UserDefaults domain

A bundled app and `swift run Pulse` use **different** defaults domains (bundle id vs process name). `LegacyDefaults` copies the old `Pulse` domain into the bundle domain **once**, only keys the new domain does not already have. After that they diverge on purpose. Details: [decisions/bundle-and-defaults.md](decisions/bundle-and-defaults.md).
